(2) Bug fix: the old filter only looked at files with an `EditText` or an NSC, so FileProvider `<paths>` files were never scanned; they are now. (4) resources.arsc is scanned through the string pool (strings only) instead of raw bytes in two encodings: fewer false positives; the AndroGoat secret formats are kept as 19 stricter ones plus Google key, Firebase URL, AWS and JWT; NOT carried over: Twilio `SK...` (collides with ordinary words), Mapbox `sk.eyJ` (looks like a JWT) and HTTP Basic (the arsc filter drops strings with spaces). (5) resource findings now carry `ruleId` and `confidence`; the same secret in several values files is reported once.
  - `VulnKnowledge`: CWE-798, 295, 319, 284 extended (text and XML samples), new card CWE-324 (pin lifecycle). `RuleRegistry.audit()` should return empty. `Capabilities.SCANNER` updated. Version 0.43.0 / code 87.

  2. **Insecure/downgraded TLS protocol version (CWE-327)** - `scanSmali`: `SSLContext.getInstance("...")` traced back to its string literal argument via the existing `argString` register-tracer; `"SSL"/"SSLv2"/"SSLv3"` -> HIGH (broken protocol, POODLE etc.), `"TLS"/"TLSv1"/"TLSv1.1"` -> MEDIUM (version-ambiguous / deprecated). Does not fire for `"TLSv1.2"`/`"TLSv1.3"` or no explicit `getInstance` call at all.
  3. **ContentProvider SQL injection via query() (CWE-89)** - `scanSmali`: inside a class that extends `ContentProvider`, if the `query()` method body both builds a string (StringBuilder/concat) and calls `rawQuery`/`execSQL`, flagged HIGH. This is the "SQL injection via content provider" bug class (distinct from the existing general "SQL built by StringBuilder" check, which is per-class/windowed and not query()-specific) - a very common AndroGoat/vulnerable-app exercise and real-world CVE pattern (an exported provider that builds SQL from the incoming Uri's path segments or the caller's selection string).
  4. **Task hijacking / StrandHogg-style (CWE-926)** - `scanManifest`, inside the existing exported-component loop: an exported `activity`/`activity-alias` with a non-empty `android:taskAffinity` AND `android:launchMode="singleTask"` or `"singleInstance"` is flagged MEDIUM. A malicious app can claim the same taskAffinity and get itself inserted into/on top of this app's task to show a convincing fake UI on a task the user believes is this app's.
  5. **Exported component "protected" by a weak custom permission (CWE-926)** - `scanManifest`: a new `declaredPerms` map (every `<permission android:name=... android:protectionLevel=...>` in the manifest, default "normal" when the attribute is absent) is cross-referenced against each exported component's `android:permission`/`readPermission`/`writePermission`. If the permission guarding it is `normal` or `dangerous` (not `signature`/`signatureOrSystem`), flagged MEDIUM - any other app can just declare `<uses-permission>` for it (silently for normal, with a one-time grant for dangerous) and use the component, so it is not a real same-app-only restriction even though a permission attribute is present (this is NOT the same as the existing "no permission at all" check, which stays HIGH/MEDIUM and does not care about protectionLevel).
  - These five are independent of the AndroGoat benchmark list (`tools/androgoat/androgoat_expected.json` is unchanged) - AndroGoat does not exercise Zip Slip/TLS downgrade/StrandHogg/weak-custom-permission, so they will not move the "N/30" count, but they are common enough in real third-party apps that they are worth having. The AndroGoat benchmark's 0.34.1 fix (Axml.kt decoder for res/ XML -> Keyboard Cache / NSC findings) is unchanged by this version; still waiting on the owner's next AndroGoat run to confirm those plus the still-open "Firebase DB" MISS.
  - Suspects if it fails to compile: the `declaredPerms` map build (`mapNotNull` with `return@mapNotNull null`, then `.toMap()`) right before the existing `compRe` loop in `scanManifest`; the Zip Slip block's `let { m -> ... }` destructuring `val (ms, me) = methodBounds(...)`; the TLS block's `continue` inside a `for` loop reading `argString(...)`; the ContentProvider block's nested `if`/`if` (two closing braces).
  - Test (owner, Android-only, same workflow as 0.33.1's on-device benchmark): (1) Deep scan (code) on any APK that extracts a zip/unzips an update or plugin - look for "Possible Zip Slip"; a clean modern app using `java.nio.file` APIs or already canonicalising should NOT fire. (3) A ContentProvider with a raw-SQL query() - try against a deliberately vulnerable sample provider if one is on hand. (4) A manifest with `taskAffinity` + `singleTask` on an exported activity (most real apps will NOT have this - it is a rare, interesting finding, not a MISS/noise concern). (5) A manifest that declares its own `<permission protectionLevel="normal">` and uses it to guard an exported component - should show "weak custom permission"; a `protectionLevel="signature"` one should NOT fire this (but should still pass the pre-existing "has a permission at all" check).
  - False-positive risk notes (same caveat as always - heuristic, not proof): Zip Slip can false-positive if the canonicalisation happens in a different method the compiler inlined differently, or if the app uses a library (e.g. Apache Commons Compress) that already does the check internally in library code (should be LIB scope, lower priority to read but still shown since Zip Slip is check #1 unconditionally - consider scoping it to APP-only in a future version if this turns out noisy on big APKs). ## Version 0.8.0 notes
- 0.8.0 (UNVERIFIED on device, not compiled by Claude - no Android SDK/network in the sandbox): new **Build tab** = rebuild + sign + install. New file `Rebuild.kt` (Rebuilder, SigningKey). Pipeline: for every dex that has edited smali (workspaces/p1/smali/<classes|classes2>/...) -> extract original dex -> assemble edited smali with `com.android.tools.smali:smali:3.0.9` (called by REFLECTION: Smali.assemble(SmaliOptions, ...), fields apiLevel/outputDexFile; assembler errors captured from System.err and shown with file/line) -> replace the edited ClassDefs inside the original dex and write a new dex with `DexPool.writeTo(path, DexFile)` (custom DexFile wrapper, Opcodes.forApi chosen from the original dex version: 035->19, 037->24, 038->26, 039->28) -> re-zip with java.util.zip (old META-INF signature files removed, resources.arsc/stored entries keep STORED and are 4-byte aligned, .so 16 KB aligned; alignment is checked live) -> sign with `com.android.tools.build:apksig:8.5.2` (v1+v2+v3, v4 off) -> verify with ApkVerifier. Build with zero edits just re-signs the original (good first test of signing/install).
- Signing key: generated inside **Android Keystore** (RSA-2048, non-exportable, system self-signed cert) instead of BouncyCastle (no new dependency). The key is lost if APK ReLab is uninstalled.
- Install: PackageInstaller session + PendingIntent broadcast (dynamic receiver, `dev.apkrelab.INSTALL_RESULT`); needs "Install unknown apps" permission for APK ReLab (the app opens that settings screen). "Uninstall orig" button (ACTION_DELETE) because the new signature can't update the original. "Export" saves signed.apk through the system file picker.
- Manifest additions: REQUEST_INSTALL_PACKAGES, REQUEST_DELETE_PACKAGES, largeHeap=true (DexPool rewrite is memory hungry).
- Limitations: split APKs/bundles (only base.apk is rebuilt); package rename not implemented; build runs in a plain Thread (screen kept on), not a foreground service yet; Play Protect may warn on install.
- If the build fails to compile: most likely suspects are `DexPool.writeTo(String, DexFile)`, the anonymous `DexFile` (getClasses/getOpcodes) in Rebuild.kt, or `com.android.tools.build:apksig:8.5.2` not resolving (try another apksig version or drop apksig.jar into app/libs).
