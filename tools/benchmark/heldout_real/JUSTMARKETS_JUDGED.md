# JustMarkets 6.15.1 (com.justmarkets) - precision read of the 0.80.0 device report, with the APK (2026-10-14)

APK sha256 336bbeb653e148f84ba5c8d8ce01e2fe8f2f4a34c4190c893ce90b51bca1c612 (the owner's device build; split APK, 6 dex, 59,667 classes, 18,766 obfuscated; NO .so in this base APK - the native libraries are in a separate ABI split the scanner never saw).
This is a TUNING app (the owner's own product), judged to answer one question: is "0 HIGH" real, or did a lowering rule hide something?

## The obfuscation-lowering question (the main risk I flagged)
Every OBF card was attributed to app vs library by its `.source` and app-package references. Of the 48 OBF cards:
- Library code wrongly in OBF scope (Google Play Services / play-core, Firebase, Facebook SDK, Lottie, Clarity, AndroidX): ~40. Lowering them is correct in effect, wrong in mechanism (they are libraries, not "likely third-party heuristic noise").
- Real JustMarkets app code, lowered as "likely third-party": **mu.h (DefaultPreference), mu.j (TradingTokenStorage), ar.c + ar.f (SocketRepository SSL), af.m (SessionInfo), qf.i0, pz.c.** These are the ones the lowering rule should NOT have touched - app code that R8 renamed.

## Were any of those app-code cards real?
- **ar.c "Hostname verification disabled" (MEDIUM, lowered to MEDIUM):** ar.c is an all-true HostnameVerifier (`verify() { return true; }`). It is installed on the TRADING websocket OkHttpClient in ar.f.p() - BUT only when `ou.a.y()` returns true, which reads a remote-config flag **"ignoreWebsocketPinningCheck"**. When the flag is off (default), the client uses a real `CertificatePinner` with pinned hashes, plus an app-level `SslCertificateVerifierInterceptor` that checks the public-key hash against a pin set. So: a remote kill-switch for the trading socket's TLS pinning + hostname check. NOT exploitable by itself (the attacker must flip a server-side flag), but it is real attack surface a reviewer must see, and the finding's own detail ("exact but ...") is right. Verdict: **TP-conditional**, correctly MEDIUM, correctly kept visible. The engine did NOT hide it.
- **mu.h / af.m / qf.i0 "token/secret stored in plain SharedPreferences":** the auth tokens (accessToken, refreshToken) are stored via plain `SharedPreferences.getString/putString` (st.r delegate, file "JustMarket.pref", MODE_PRIVATE), no EncryptedSharedPreferences, no Cipher. `allowBackup=false` + dataExtractionRules limit off-device theft, so impact needs a rooted / malware-present device. Verdict: **TP-low**, correctly MEDIUM/LOW.
- **mu.j TradingTokenStorage:** the trade tokens here ARE signed with HmacSHA256 using a KeyStore key (constructor takes a `java.security.KeyStore`), stored base64 in prefs. The HMAC is integrity, not confidentiality, but this is better than mu.h. The "high-entropy string" card on mu.h is the 34-char `getAccessToken()` descriptor string - a FP (it is a method-signature literal, not a secret).

## App-scope (not obfuscated) HIGH/MEDIUM
- 2 x `webview-js-interface` (MainActivity bridge `AndroidNative` -> SpaJavaScriptInterface: logout / onSyncRefreshToken / userHasBeenBlocked / onGetFeatureList; TradeChartSlideFragment -> TradingViewChartJavaScriptInterface: chart callbacks). Both MEDIUM (0.78.0: bridge in another class, no dangerous API in the exposed methods). Read: the exposed methods do app-internal things (refresh token via the app, feature list), none take a path / URL / reflection arg. The WebView loads a fixed app URL. Verdict: both **correctly MEDIUM**; the SPA bridge (onSyncRefreshToken) is worth a manual look but is not a file/exec/redirect sink.

## Conclusion
"0 HIGH" is **honest for this build**: no app-code finding rises to HIGH under the current rules, and the one piece of real attack surface (the remote TLS-pinning kill-switch) is reported at MEDIUM and visible. The obfuscation-lowering rule DID fire on ~6 real app-code cards, but all of them were already LOW/MEDIUM by their own rule, so the lowering changed confidence wording, not the verdict - no HIGH was hidden.
HOWEVER the mechanism is wrong and will hide a real HIGH in a more vulnerable obfuscated app. **0.82.0 candidate: the "obfuscated = likely third-party" lowering must not fire on a class whose `.source` or package references tie it to the app** (here: 163 `com.justmarkets` refs in mu.h). Attribute obfuscated classes to app vs library by source-file / string / xref evidence, not by the renamed name alone.
Limits confirmed (for the report's preamble): native ABI split not analysed; cross-group taint losses reported as 0 but 506 hubs + 14 marked hubs not expanded; business-logic and server-side bugs out of scope.
